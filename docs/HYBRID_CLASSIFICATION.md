# 混合商品分类建议（2026-10-25）

## 用户如何使用

发布或编辑时填写标题，点击“智能推荐分类”。系统最多展示三个分类按钮和匹配依据，点击其中一个才会修改表单；仍需点击发布或保存。
描述继续选填，不参与预测。手动分类始终可用。

- “马赛克”：可以匹配马赛克艺术画，结合模型给出艺术品建议，不保证所有语境都正确。
- “琴”或“闲置琴”：可出现乐器、玩具两个候选。
- “玩具琴”：具体词优先，不因包含“琴”就先归乐器。
- 模型不可用或忙碌：仅明确的多字完整词/别名匹配可降级返回，界面标注“当前为词库匹配建议”。
- 仅单字、片段等弱匹配在模型故障时不返回候选，允许手动选择。
- 推荐接口允许短标题；发布表单原有标题最少 2 字规则保留，因此单字可试分类，实际发布需补充商品名称。

标题变更、手动改分类、关闭弹窗、切换编辑商品都会废弃旧响应。仅修改描述不会清除建议或重新请求。

## 数据与边界

词库在 `app/data/category_lexicon/` 的九个 JSON 文件中。每类 100 个主词，共 900 个；十类名称不变，“其他”不建词表。上下文没有完整原词表，因此根据通用知识补齐 900 词，并非逐字复用原列表，新增常见别名独立保存，不计入主词数。

来源：**Agent 根据通用商品知识整理，未经真实词频统计**。不是交易平台高频排名、不是独立人工标注、不是模型训练数据。部分条目专业、同义或上下位概念相近（例如手机/智能手机），均不能证明真实商品分布。

每条记录有稳定 id、主词 term 和 aliases；所属类别来自文件 category。修改词序时不要重编号。别名按大小写、全半角和空白规范化后检查冲突，不允许静默覆盖。词库不完整或非法只使分类功能不可用，网站可启动。

边界集中在 `app/services/category_policy.py`：
生活电器→家居用品；数码配件→电子产品；普通鞋包→服装；专用运动装备→运动器材；演奏设备及专用配件→乐器；读物→书籍；创作/维修工具→工具；作品成品→艺术品；娱乐模型/声光玩具→玩具。
这些是项目约定，实际用户可能有不同理解；最终分类由用户选择。

## 匹配、模型与降级

1. `category_lexicon.py` 懒加载词库并建立连续片段索引，进程内复用。
2. 标题规范化后按组合分隔符处理。优先完整词/别名，长词覆盖同一范围内的短词，例如篮球鞋覆盖篮球，玩具琴覆盖琴。完整匹配保留独立商品词，可能产生多个类别。
3. 没有完整匹配的片段，移除少量常见出售修饰词，取覆盖剩余片段至少一半的最长连续匹配。一般至少两字；仅“琴、鼓、笛、箫、埙、笙、阮”允许单字片段。
4. 宽泛片段不参与匹配。小号/大号与明确商品同时出现时不额外当成乐器；单独输入仍可能因歧义而拒绝。
5. 每类只取最强匹配和最多两个依据，不按命中数量求和。九百个主词不是九百个模型候选。
6. 最多六个检索类别参与模型评分，超过则提示补充名称。每类使用最有代表性的商品词构造中文 NLI 假设“这段文字描述的是…。”，加现有五个拒绝假设。完整类别长说明在最初冒烟实验中导致过多拒绝，因此采用短商品表述，而非新增多组类别系统。
7. 模型仍为本地 mDeBERTa，revision `8adb042d524ecd5c26d3e3ba0e3fbcf7e2d0864c`。由真实 config.id2label 确认 entailment=0、neutral=1、contradiction=2。没有训练或微调。官方说明位于模型目录 README，也见 [模型主页](https://huggingface.co/MoritzLaurer/mDeBERTa-v3-base-mnli-xnli)。
8. 对匹配类别独立计算 entailment/contradiction 二项 softmax 支持度；该数值忽略 neutral，可能偏高，**不是正确概率**。支持度至少 0.55。非商品意图候选相对分数超过 0.8 且商品相对分数低于 0.05 时否决。泛化的“信息不明确的东西”不直接否决有词库证据的短标题。
9. 先按匹配层级（完整/别名、片段、单字），同层级由模型支持度排序，再按匹配长度打破并列。两种分数不相加。若超过三个候选且第三、第四同层级的支持分差不足 0.15，返回不确定，不能随便截前三。
10. 无词库候选时沿用固定十类别＋拒绝候选的语义回退；原相对分数/支持/分差阈值 0.45/0.70/0.25 只用于这个固定候选回退。“书籍”回退说明去掉文具以符合本次边界，其余短语保持。
11. 功能关闭直接返回 503。模型缺失、异常或锁忙时，只有 1～3 个明确完整/别名候选才能返回词库建议；否则维持 503/429。词库损坏不会静默跳过验证。
12. 求购、招聘、招生、寻物等明显非商品发布意图使用独立输入规则过滤，并保留 NLI 拒绝候选。不是商品类别关键词规则。该过滤仍可能误拒绝口语表达，不是通用意图理解器。

匹配和模型分别提供证据，均可能出错。词库没有包含的同义说法可能进入效果较弱的原模型回退。不能把词库覆盖提升描述为模型自身准确率提高。

## 接口与兼容

POST `/api/v1/items/category-suggestion`，现有 JWT 登录保护，只接收 title 用于计算；额外 description 被忽略。原请求体 8192 字节及标题 50 字符限制保留。

响应增加：
- candidates：最多三个对象，各含 category、source、evidence、reason。
- source：hybrid（词库＋模型）、model（纯语义回退）、lexicon（模型不可用时词库降级）、none。
- degraded：是否降级；version：hybrid-v1。
- 保留 status、category、message；只有恰好一个候选时旧 category 才有值，多候选时为 null。旧页面不会自动采用多候选的第一项；新页面能读取旧单候选结构。

启动器检查 `category-suggestion-hybrid-v3`，健康接口同时保留 v2 标记以兼容旧调用方。模型是否已加载与网站健康分开。不要只刷新旧后端就认为服务已经更新。

## 性能与配置

使用原 Python 环境、Torch 2.6.0+cpu、Transformers 4.57.6，无新增依赖、模型下载、量化或数据库迁移。
每个应用实例一把推理锁，模型首次请求加载；实际推理结束才释放锁。客户端取消或 45 秒超时不会终止后端计算。多进程会各自占用模型内存。

`app/config.py`：
- CLASSIFICATION_BATCH_SIZE=8（运行时检查 1～32）。
- CLASSIFICATION_HYBRID_MIN_SUPPORT=0.55。
- 原 CLASSIFICATION_ENABLED、MODEL_PATH、THREADS 及固定语义回退阈值继续有效。

更改这些值需重启并复测，不能认为旧阈值适用于任何候选说明。缓存最多 128 组候选假设的 token，不缓存用户标题。默认日志只记录异常类型与耗时。
